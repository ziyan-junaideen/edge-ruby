### The snapshot is not reproducible from a commit

`openapi.json` is **gitignored** upstream — by the monorepo root `.gitignore:8`,
not by `ept/.gitignore` — and has never been tracked
(`git check-ignore -v ept/openapi.json`, `git ls-files --error-unmatch`). It is a
local build artifact produced by `open_api_spex` from
`CoreHTTP.OpenAPISpec`, so its contents reflect whatever working tree existed
when someone last generated it — not the commit that happens to be checked out
now.

Its mtime (2026-08-19) is eleven days older than the checkout it was copied
from, and it does not match `main` either.

### It was generated from an abandoned branch

The snapshot documents `payment_demands.amount_refunded_cents`, with a
description of partial-refund balance tracking. That field exists **nowhere** in
the shipped source:

```
$ git grep -c amount_refunded_cents main  -- ept/lib   # no output
$ git grep -c amount_refunded_cents HEAD  -- ept/lib   # no output
$ git grep -c amount_refunded_cents backup/edg-4035-partial-refunds-wip-20260819 -- ept/lib
ept/lib/core/transactions.ex:2
ept/lib/core/transactions/payment_demand.ex:5
ept/lib/core/transactions/refund_backfill.ex:4
```

It exists only on `backup/edg-4035-partial-refunds-wip-20260819`, a WIP branch
that was not merged. **The snapshot therefore describes behaviour that no
deployed server has.** Treat every claim in it as unverified until it is
confirmed against the Phoenix source or sandbox.

This is why `contract/manifest.yml`, derived from the source tree, is this
client's source of truth and the snapshot is only a cross-check.

### Regenerating

From an `ept` checkout of the branch you intend to target:

```sh
cd /path/to/edge/ept
mix openapi.spec.json --spec CoreHTTP.OpenAPISpec openapi.json
```

Then re-copy it here, update the table above, and regenerate the manifest.
Record which branch it came from — that is the field that was missing and cost
us a wrong fact.

## The manifest

`contract/manifest.yml` is generated by `contract/bin/extract_manifest.rb` from
the Phoenix views, controllers and schemas, cross-checked against the snapshot.

```sh
contract/bin/extract_manifest.rb /path/to/edge/ept > contract/manifest.yml
```

Regenerated at Edge `83641f3d887e02e021805e97d2fe78a54d5825d3`: 30 resources,
246 attributes (30 of them `readonly`), 76 relationships, 15 warnings.

### What it can and cannot assert

| Fact | Derivable? | From |
| --- | --- | --- |
| Which operations a resource supports | yes | routed paths |
| Custom actions | yes | routed paths |
| Relationship target, cardinality, writeability | yes | view `relationships/0`, `readonly: true`, `has: :many` |
| Attribute names and types | yes | view `fields/0`, following `*_view_fields/1` pipes |
| Attribute **readonly**ness | yes | `readonly: true` in the field spec |
| Attribute **writability** on create vs update | **no** | not expressed anywhere in the server source |
| Enum values | mostly | the module attribute behind the accessor |
| Request body shape | **no** | every write in the snapshot has `requestBody: null` |

Attribute writability by operation is the one thing neither source can answer.
Explicit per-operation payloads in each resource class are the answer, not
inference.

### Warnings are signal

The generator reports what it could not resolve instead of guessing. All fifteen
current warnings are understood:

**The `financial_institutions` type collision (8 warnings) — a live server bug.**
`lib/core_http/views/financial_institutions.ex:12` declares
`def type(), do: "beneficial_owners"`. Consequences:

- `GET /v2/financial_institutions` returns objects whose `data.type` is
  `beneficial_owners`.
- The spec generator emits no `financial_institutions_*` schema at all. All four
  paths share one schema:

  ```
  /v2/beneficial_owners        get  -> beneficial_owners_collection
  /v2/beneficial_owners        post -> beneficial_owners_member
  /v2/beneficial_owners/{id}   get  -> beneficial_owners_member
  /v2/financial_institutions   get  -> beneficial_owners_collection
  ```

- **The collision resolved in favour of the financial institution.**
  `beneficial_owners_member` holds `created_at`, `icon_url`, `login_url`,
  `logo_url`, `name`, `primary_colour`, `state`, `updated_at` — the
  financial-institution fields — and does not hold `ownership_percentage`. So
  `/v2/financial_institutions` is documented with the *right* fields under a
  misleading schema name, and **`/v2/beneficial_owners` is the endpoint whose
  published schema is wrong.**
- That is why the six financial-institution fields surface as "in the snapshot
  but not in the view" against `beneficial_owners`: the manifest is comparing
  the real beneficial-owner view to a schema that describes something else.

For this client it means a `data.type` -> class registry cannot be the only way
a response is identified: the requested route has to disambiguate. Filed as
release blocker RB-3.

**`amount_refunded_cents` (1 warning).** WIP-branch contamination, above.

**Computed enums (2 warnings).** `payment_methods.kind`
(`payment_method.ex:40`) and `red_flags.violation` (`red_flag.ex:25`) are built
at compile time from concatenated attributes
(`@violations @edge_violations ++ @legit_script_violations`). They fall back to
the snapshot and are marked `values_from: openapi-snapshot`. Since the client
must accept unknown enum values anyway, this is a documentation gap, not a
correctness one.

**An ambiguous accessor (2 warnings).**
`Core.Transactions.PaymentSubscription.billing_periods/0` is injected by a macro
in `Core.Transactions.Payment`, and `billing_periods/0` is also defined by
`Core.Purchases.Link`. The generator refuses to resolve from source when more
than one module defines an accessor it cannot attribute, and says so.
`payment_subscriptions.billing_period` therefore falls back to the snapshot.
The two lists happen to be identical today — which is precisely why resolving by
first-match would have looked correct until it wasn't.

**An undocumented replay contract (2 warnings).** `payment_subscriptions` and
`meter_ticks` both carry an `idempotency_key` field, but neither documents what
replaying a key does. `meter_ticks` says only that the key "needs to be unique",
which is a constraint, not a replay guarantee. They stay out of the idempotency
list and their writes stay non-retryable.

### Drift already found

Comparing the source against the snapshot, one genuine divergence:

| Field | Source | Snapshot |
| --- | --- | --- |
| `refund_demands.reason` | adds `custom` | 7 values |

`refund_demands.reason_note` (max 500 characters) is likewise present in the
source and absent from the snapshot. Both arrived in
`8372ac06c76b5273ec36c365079759fdaa83010e`, after the snapshot was generated.

Fields where the two disagree carry `snapshot_stale: true` and a
`snapshot_values` list, so the difference stays visible rather than being
silently resolved.
